# B200 (SM100) architecture overview

This doc collects the B200 hardware numbers and mechanisms the course uses, and marks which lab covers each. Every number states its source type:

| Mark | Meaning |
|---|---|
| **Spec** | A value from NVIDIA documentation or reported by `cudaGetDeviceProperties` |
| **Nominal** | A datasheet peak. Real kernels do not reach it; use it only to estimate an upper bound |
| **Measured** | A value the course lessons measured on our B200. Your numbers may differ slightly with clock and load |
| **Estimated** | A value derived from other numbers |

The B200's compute capability is **10.0**, that is, **SM100**. The course compiles with `-gencode=arch=compute_100a,code=sm_100a`; instructions such as `tcgen05` and TMEM are available only on targets with the `a` suffix.

## 1. Overall structure

```
                                       B200
┌────────────────────────────────────────────────────────────────────────────────┐
│  GPC ┌────┐┌────┐     GPC ┌────┐┌────┐     148 SMs, spread over several GPCs   │
│      │ SM ││ SM │ …       │ SM ││ SM │ …   a cluster must sit in one GPC       │
│      └────┘└────┘         └────┘└────┘                                         │
│  ─────────────────────────────── L2 126 MB ──────────────────────────────────  │
│  ───────────────────────── HBM3e, nominal 8 TB/s ────────────────────────────  │
└────────────────────────────────────────────────────────────────────────────────┘
```

| Item | Value | Source | Covered in |
|---|---|---|---|
| SM count | 148 | Spec (`./lab doctor` prints it) | [00](../course/00_transpose/README.md) |
| Max SM clock | 1965 MHz | Spec (`nvidia-smi -q -d CLOCK`); measured still 1965 MHz during fully loaded timing | [10 §3.3](../course/10_simt_gemm/README.md) |
| L2 | 126 MB (132,644,864 bytes), shared by the whole chip | Spec | [11 §4.1](../course/11_naive_attention/README.md), [32 §3.3](../course/32_ws_gemm/README.md) |
| HBM3e capacity | About 178 GiB usable | Spec (`totalGlobalMem`) | [11](../course/11_naive_attention/README.md) |
| HBM bandwidth | 8 TB/s | Nominal | [00 §3](../course/00_transpose/README.md) |
| HBM bandwidth (contiguous copy `y.copy_(x)`) | About 6.4–6.5 TB/s | Measured | [00 §3](../course/00_transpose/README.md), [30 §3.1](../course/30_tma_mbarrier/README.md) |
| HBM access latency | On the order of a few hundred ns to 1 µs (the lessons estimate with 700 ns) | Estimated | [00 §4.5](../course/00_transpose/README.md) |

The `% peak` column of `./lab bench` is computed against the nominal 8 TB/s. So a memory-bound kernel at about 80% `% peak` is already close to the measured upper bound of a contiguous copy.

## 2. What is inside one SM

```
                                One SM
┌────────────────────────────────────────────────────────────────────┐
│  SMSP 0      SMSP 1      SMSP 2      SMSP 3     4 warp schedulers  │
│  Register file: 65536 × 32 bit = 256 KB                            │
│  FP32 units: 128 FMA per cycle      MUFU: 16 exp2 etc. per cycle   │
│  Tensor Core (shared by mma.sync and tcgen05.mma)                  │
│  TMEM: 128 lanes × 512 columns × 32 bit = 256 KB                   │
│  shared memory + L1: up to 228 KB of shared memory                 │
│  TMA unit                                                          │
└────────────────────────────────────────────────────────────────────┘
```

| Resource | Per SM | Per block / per thread | Source | Covered in |
|---|---|---|---|---|
| Threads | Up to 2048 (64 warps) | Up to 1024 per block | Spec | [00 §4.1](../course/00_transpose/README.md) |
| Resident blocks | Up to 32 | — | Spec | [00 §5](../course/00_transpose/README.md) |
| Warp schedulers (SMSP) | 4 | — | Spec | [20 §4.1](../course/20_mma_gemm/README.md) |
| Registers | 65536 × 32-bit = 256 KB | Up to 255 per thread | Spec | [01 §4.3](../course/01_softmax/README.md) |
| shared memory | 228 KB | Up to 227 KB per block; more than 48 KB must be requested explicitly | Spec | [21 §4.4](../course/21_pipeline_gemm/README.md) |
| shared memory banks | 32, each 4 bytes wide | — | Spec | [00 §4.3](../course/00_transpose/README.md) |
| TMEM | 128 lanes × 512 columns × 32 bit = 256 KB | Allocated by column | Spec (PTX ISA) | [31 §4.1](../course/31_tcgen05_gemm/README.md) |

**Residency (occupancy)**: how many blocks one SM can hold at the same time depends on the tightest of three limits: registers, shared memory and thread count. For example, if a block uses 225 KB of shared memory, each SM can hold only 1 such block ([32 §5.1](../course/32_ws_gemm/README.md)).

**shared memory and L1 share the same storage**. The driver chooses the split between them (the carveout) per kernel; a kernel that needs a large shared memory can state its preference with `cudaFuncAttributePreferredSharedMemoryCarveout` ([21 §4.4](../course/21_pipeline_gemm/README.md)).

| MUFU (`ex2.approx`, `lg2`, `rcp`, etc.) | 16 per SM per cycle, 1/8 of FP32 FMA | Spec ([CUDA Best Practices throughput table](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#throughput-of-native-arithmetic-instructions)) | [01 §4.4](../course/01_softmax/README.md), [34 §3.3](../course/34_fa3/README.md) |

### 3.1 The ridge point: compute or bandwidth

**Arithmetic intensity** is how many floating-point operations a kernel performs per byte it moves (FLOP/B). The **ridge point** is the peak compute divided by the peak bandwidth. A kernel whose arithmetic intensity is below the ridge point is bandwidth-bound; one above it is compute-bound.

| Unit | Nominal peak | ÷ 8 TB/s = ridge point |
|---|---|---|
| FP32 CUDA core | 75 TFLOP/s | About 9 FLOP/B |
| BF16 Tensor Core | 2250 TFLOP/s | About 280 FLOP/B |

Moving to Tensor Cores raises the ridge point about 30×: an algorithm that was compute-bound may now be bandwidth-bound. This is why FlashAttention reduces HBM reads and writes ([11 §3.5](../course/11_naive_attention/README.md), [10 §3.3](../course/10_simt_gemm/README.md)).

### 3.2 Why the exponential becomes a bottleneck

Attention computes one `exp` for every score. The GPU computes `2^x` with the MUFU `ex2`, then converts with `e^x = 2^(x·log₂e)` ([01 §4.4](../course/01_softmax/README.md), [22 §3.3](../course/22_fa2/README.md)).

For one 128×128 score block (D = 128):

| Work | Approximate cycles per SM |
|---|---|
| S = Q·Kᵀ (128×128×128) | 512 |
| O += P·V (128×128×128) | 512 |
| 16384 `exp2`, 16 per cycle | 1024 |

The two GEMMs together take about as long as the exponentials. So once Tensor Cores are fast enough, **softmax becomes the bottleneck** ([34 §3.3](../course/34_fa3/README.md)). FA4 computes part of the `exp2` with an FMA polynomial to take load off MUFU ([lab 41](../course/41_fa4_softmax/README.md)).

## 4. Three generations of Tensor Core instructions

| Instruction | Architecture | Issued by | Operands come from | Accumulator lives in | Completion | Covered in |
|---|---|---|---|---|---|---|
| `mma.sync` | Since Ampere, still supported on B200 | One warp | Registers (`ldmatrix` first) | Registers | Synchronous: usable when the instruction returns | [20](../course/20_mma_gemm/README.md) |
| `wgmma.mma_async` | Hopper (SM90) only | 4 warps | shared memory / registers | Registers | Asynchronous | Not covered (not on B200) |
| `tcgen05.mma` | Blackwell (SM100) | **One thread** | shared memory (descriptors) / TMEM | **TMEM** | Asynchronous: `tcgen05.commit` signals an mbarrier | [31](../course/31_tcgen05_gemm/README.md) |

On B200, even a perfect `mma.sync` kernel reaches only about 0.36–0.39× of cuBLAS (measured, [20 §4.1](../course/20_mma_gemm/README.md)). Part 2 uses `mma.sync` to learn fragment layouts, swizzle and pipelines; Part 3 switches to `tcgen05` to get past this limit.

One `tcgen05.mma` instruction is at most 128×256×16 (single CTA); when two CTAs cooperate (`cta_group::2`), M can reach 256 ([33 §4.4](../course/33_2cta_gemm/README.md)).

## 5. Tensor Memory (TMEM)

TMEM is storage on each SM reserved for `tcgen05`; it holds MMA accumulators.

```
          column 0                                  column 511
lane   0  ┌───────────────────────────────────────────────┐   ← warp 0 (% 4) can access only lanes 0–31
  ...     │      each cell is 32 bit                      │   ← warp 1: lanes 32–63
lane 127  └───────────────────────────────────────────────┘   ← warp 2: 64–95, warp 3: 96–127
TMEM address = (lane << 16) | column
```

| Rule | Details | Covered in |
|---|---|---|
| Allocation is by column | `tcgen05.alloc` allocates a power-of-two number of columns (32–512) at a time, always including all 128 lanes; you must `dealloc` when done | [31 §4.1](../course/31_tcgen05_gemm/README.md) |
| Access is split by warp | Warp w can access only lanes `32·(w%4)` to `32·(w%4)+31` | [31 §4.2](../course/31_tcgen05_gemm/README.md) |
| Reads and writes are asynchronous | After `tcgen05.ld`/`st` you need `tcgen05.wait::ld`/`wait::st` | [31 §4.6](../course/31_tcgen05_gemm/README.md), [34 §4.5](../course/34_fa3/README.md) |
| Handoff between threads needs fences | `tcgen05.fence::before_thread_sync` → synchronize → `tcgen05.fence::after_thread_sync` | [31 §4.7](../course/31_tcgen05_gemm/README.md), [34 §4.7](../course/34_fa3/README.md) |

512 columns means the TMEM of one SM holds only two 128×256 FP32 accumulators. Lab 32 uses it for accumulator double buffering ([32 §4.4](../course/32_ws_gemm/README.md)), and lab 34 puts S and O in it ([34 §5.1](../course/34_fa3/README.md)).

## 6. TMA and mbarrier

**TMA (Tensor Memory Accelerator)** is SM hardware dedicated to moving multidimensional blocks of data. One thread issues one instruction, and the hardware moves the whole box between global and shared memory; other threads do not take part ([30 §4.1–4.2](../course/30_tma_mbarrier/README.md)).

| Concept | Details |
|---|---|
| tensor map | A 128-byte descriptor, encoded once on the host with `cuTensorMapEncodeTiled`, that describes the tensor's shape, strides, box size and swizzle |
| box | The block of data moved at a time, at most 256 elements per dimension |
| swizzle | When writing to shared memory, permutes the positions of 16-byte chunks by XOR to avoid bank conflicts; `tcgen05` operands also require this layout ([30 §4.3](../course/30_tma_mbarrier/README.md)) |
| multicast | One read is written into the shared memory of several CTAs in the cluster at once ([33 §4.5](../course/33_2cta_gemm/README.md)) |

An **mbarrier** is an 8-byte synchronization object in shared memory. It records the current phase, the pending arrival count, and the pending byte count (tx-count). When both reach zero, the phase completes and the parity flips; waiters use the parity to tell whether it has completed ([30 §4.4](../course/30_tma_mbarrier/README.md)).

TMA loads and `tcgen05.commit` both send their completion signal to an mbarrier. So the mbarrier is the "relay baton" of every asynchronous pipeline in Parts 3 and 4.

**proxy**: ordinary `ld`/`st` belong to the generic proxy; TMA and `tcgen05` belong to the async proxy. When ordinary instructions write a region of shared memory and TMA then reads it, every writing thread must first execute `fence.proxy.async.shared::cta` ([30 §4.5](../course/30_tma_mbarrier/README.md)). Tests and racecheck often both miss this kind of bug (see [Tools guide §3.1](tools.md#31-what-the-sanitizer-cannot-see)).

## 7. Clusters and CTA pairs

A **cluster** is a group of CTAs that are guaranteed to run at the same time and are placed on the same GPC ([33 §4.1](../course/33_2cta_gemm/README.md)).

| Item | Value / details | Source |
|---|---|---|
| Cluster size | Portable limit of 8 CTAs | Spec |
| DSMEM | CTAs in a cluster can access each other's shared memory and arrive on each other's mbarriers | Spec |
| CTA pair | 2 CTAs form a pair; one thread of the leader issues `tcgen05.mma.cta_group::2`, and together they compute one 256×256 tile. Half of A and of B each sit in the partner's shared memory, so the two SMs share one copy of B | [33 §4.4](../course/33_2cta_gemm/README.md) |
| Residency | With 1 CTA per SM (225 KB smem): cluster 2 → 74 clusters (all 148 SMs used); cluster 4 → 33 clusters (only 132 SMs used) | Measured (`cudaOccupancyMaxActiveClusters`) |

Cluster 4 cannot fill all 148 SMs because the number of usable SMs per GPC is not always a multiple of 4.
