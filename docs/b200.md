# B200（SM100）架构概览

本文汇总课程用到的 B200 硬件数字和机制，并标出哪一关讲它。每个数字注明来源类型：

| 标记 | 含义 |
|---|---|
| **规格** | NVIDIA 文档或 `cudaGetDeviceProperties` 报告的值 |
| **标称** | 数据手册的峰值。实际 kernel 达不到，只用来估算上界 |
| **实测** | 课程讲义在本机 B200 上测得的值。你的数字可能因频率、负载略有不同 |
| **估算** | 由其他数字推出来的值 |

B200 的计算能力（compute capability）是 **10.0**，即 **SM100**。课程用 `-gencode=arch=compute_100a,code=sm_100a` 编译；`tcgen05`、TMEM 等指令只在带 `a` 后缀的目标上可用。

## 1. 全局结构

```
                                    B200
┌────────────────────────────────────────────────────────────────────────────┐
│  GPC ┌────┐┌────┐     GPC ┌────┐┌────┐            148 个 SM，分布在若干 GPC  │
│      │ SM ││ SM │ …       │ SM ││ SM │ …          一个 cluster 必须放在同一 GPC│
│      └────┘└────┘         └────┘└────┘                                      │
│  ─────────────────────────── L2 126 MB ──────────────────────────────────── │
│  ─────────────────────────── HBM3e，标称 8 TB/s ───────────────────────────── │
└────────────────────────────────────────────────────────────────────────────┘
```

| 项目 | 数值 | 来源 | 哪一关讲 |
|---|---|---|---|
| SM 数 | 148 | 规格（`./lab doctor` 会打印） | [00](../course/00_transpose/README.md) |
| SM 时钟上限 | 1965 MHz | 规格（`nvidia-smi -q -d CLOCK`）；满载计时时实测仍为 1965 MHz | [10 §3.3](../course/10_simt_gemm/README.md) |
| L2 | 126 MB（132,644,864 字节），全芯片共享 | 规格 | [11 §4.1](../course/11_naive_attention/README.md)、[32 §3.3](../course/32_ws_gemm/README.md) |
| HBM3e 容量 | 约 178 GiB 可用 | 规格（`totalGlobalMem`） | [11](../course/11_naive_attention/README.md) |
| HBM 带宽 | 8 TB/s | 标称 | [00 §3](../course/00_transpose/README.md) |
| HBM 带宽（连续拷贝 `y.copy_(x)`） | 约 6.4–6.5 TB/s | 实测 | [00 §3](../course/00_transpose/README.md)、[30 §3.1](../course/30_tma_mbarrier/README.md) |
| HBM 访问延迟 | 几百 ns 到 1 µs 量级（讲义按 700 ns 估算） | 估算 | [00 §4.5](../course/00_transpose/README.md) |

`./lab bench` 的 `% peak` 列按标称 8 TB/s 计算。所以访存型 kernel 的 `% peak` 到 80% 左右就已经接近连续拷贝的实测上限。

## 2. 一个 SM 里有什么

```
                         一个 SM
┌──────────────────────────────────────────────────────────────┐
│  SMSP 0      SMSP 1      SMSP 2      SMSP 3     4 个 warp 调度器 │
│  寄存器堆：65536 × 32 bit = 256 KB                              │
│  FP32 单元：每周期 128 个 FMA      MUFU：每周期 16 个 exp2 等     │
│  Tensor Core（mma.sync 与 tcgen05.mma 共用）                   │
│  TMEM：128 lane × 512 列 × 32 bit = 256 KB                     │
│  shared memory + L1：shared memory 最多 228 KB                 │
│  TMA 单元                                                      │
└──────────────────────────────────────────────────────────────┘
```

| 资源 | 每 SM | 每 block / 每线程 | 来源 | 哪一关讲 |
|---|---|---|---|---|
| 线程 | 最多 2048（64 个 warp） | 每 block 最多 1024 | 规格 | [00 §4.1](../course/00_transpose/README.md) |
| 驻留 block | 最多 32 | — | 规格 | [00 §5](../course/00_transpose/README.md) |
| warp 调度器（SMSP） | 4 | — | 规格 | [20 §4.1](../course/20_mma_gemm/README.md) |
| 寄存器 | 65536 个 32 位 = 256 KB | 每线程最多 255 个 | 规格 | [01 §4.3](../course/01_softmax/README.md) |
| shared memory | 228 KB | 每 block 最多 227 KB；超过 48 KB 要显式申请 | 规格 | [21 §4.4](../course/21_pipeline_gemm/README.md) |
| shared memory bank | 32 个，每个 4 字节宽 | — | 规格 | [00 §4.3](../course/00_transpose/README.md) |
| TMEM | 128 lane × 512 列 × 32 bit = 256 KB | 按列分配 | 规格（PTX ISA） | [31 §4.1](../course/31_tcgen05_gemm/README.md) |

**驻留（occupancy）**：一个 SM 能同时放多少个 block，取决于寄存器、shared memory、线程数三者中最紧的一个。例如一个 block 用了 225 KB shared memory，每个 SM 就只能放 1 个这样的 block（[32 §5.1](../course/32_ws_gemm/README.md)）。

**shared memory 与 L1 共用同一块存储**。两者的划分（carveout）由驱动按 kernel 选择；需要大 shared memory 的 kernel 可以用 `cudaFuncAttributePreferredSharedMemoryCarveout` 表明偏好（[21 §4.4](../course/21_pipeline_gemm/README.md)）。

## 3. 计算吞吐

| 单元 | 吞吐 | 来源 | 哪一关讲 |
|---|---|---|---|
| FP32 FMA（CUDA core） | 每 SM 每周期 128 个 → 148 × 128 × 2 × 1.965 GHz ≈ 74.4 TFLOP/s；`./lab bench` 按 75 TFLOP/s 计 | 规格 + 估算 | [10 §3.3](../course/10_simt_gemm/README.md) |
| BF16/FP16 Tensor Core，稠密 | 2250 TFLOP/s，约每 SM 每周期 8192 FLOP | 标称 | [20 §4.1](../course/20_mma_gemm/README.md)、[31 §3.2](../course/31_tcgen05_gemm/README.md) |
| FP8（E4M3）Tensor Core，稠密 | 4500 TFLOP/s | 标称 | [44](../course/44_fa4_fp8/README.md) |
| `mma.sync` BF16 的上限（只发 MMA 的微基准） | 约 560 TFLOP/s，标称的约 25% | 实测 | [20 §4.1](../course/20_mma_gemm/README.md) |
| cuBLAS BF16 GEMM（用 `tcgen05`） | 约 1440 TFLOP/s（4096³）、约 1550 TFLOP/s（8192×8192×4096） | 实测 | [20 §4.1](../course/20_mma_gemm/README.md) |
| MUFU（`ex2.approx`、`lg2`、`rcp` 等） | 每 SM 每周期 16 个，是 FP32 FMA 的 1/8 | 规格（[CUDA Best Practices 吞吐表](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#throughput-of-native-arithmetic-instructions)） | [01 §4.4](../course/01_softmax/README.md)、[34 §3.3](../course/34_fa3/README.md) |

### 3.1 屋脊点：算力还是带宽

**算术强度**是一个 kernel 每搬 1 字节做多少次浮点运算（FLOP/B）。**屋脊点**是峰值算力除以峰值带宽。算术强度低于屋脊点的 kernel 受带宽限制，高于它的受算力限制。

| 单元 | 标称峰值 | ÷ 8 TB/s = 屋脊点 |
|---|---|---|
| FP32 CUDA core | 75 TFLOP/s | 约 9 FLOP/B |
| BF16 Tensor Core | 2250 TFLOP/s | 约 280 FLOP/B |

换成 Tensor Core 后，屋脊点提高了约 30 倍：同一个算法，原来受算力限制，现在可能受带宽限制。这就是 FlashAttention 要减少 HBM 读写的原因（[11 §3.5](../course/11_naive_attention/README.md)、[10 §3.3](../course/10_simt_gemm/README.md)）。

### 3.2 指数为什么会成为瓶颈

attention 中每个分数都要算一次 `exp`。GPU 用 MUFU 的 `ex2` 计算 `2^x`，再用 `e^x = 2^(x·log₂e)` 换算（[01 §4.4](../course/01_softmax/README.md)、[22 §3.3](../course/22_fa2/README.md)）。

一个 128×128 的分数块（D = 128）：

| 工作 | 每 SM 约多少周期 |
|---|---|
| S = Q·Kᵀ（128×128×128） | 512 |
| O += P·V（128×128×128） | 512 |
| 16384 次 `exp2`，每周期 16 个 | 1024 |

两个 GEMM 加起来的时间与指数相当。所以 Tensor Core 足够快之后，**softmax 成为瓶颈**（[34 §3.3](../course/34_fa3/README.md)）。FA4 用 FMA 多项式算一部分 `exp2` 来分担 MUFU（[41 关](../course/41_fa4_softmax/README.md)）。

## 4. 三代 Tensor Core 指令

| 指令 | 架构 | 谁发起 | 操作数从哪来 | 累加器在哪 | 完成方式 | 哪一关讲 |
|---|---|---|---|---|---|---|
| `mma.sync` | Ampere 起，B200 仍支持 | 一个 warp | 寄存器（先 `ldmatrix`） | 寄存器 | 同步：指令返回即可用 | [20](../course/20_mma_gemm/README.md) |
| `wgmma.mma_async` | 仅 Hopper（SM90） | 4 个 warp | shared memory / 寄存器 | 寄存器 | 异步 | 不讲（B200 上没有） |
| `tcgen05.mma` | Blackwell（SM100） | **一个线程** | shared memory（描述符）/ TMEM | **TMEM** | 异步：`tcgen05.commit` 通知 mbarrier | [31](../course/31_tcgen05_gemm/README.md) |

在 B200 上，一个完美的 `mma.sync` kernel 也只能达到 cuBLAS 的约 0.36–0.39 倍（实测，[20 §4.1](../course/20_mma_gemm/README.md)）。部分 2 用 `mma.sync` 学 fragment 布局、swizzle 和流水；部分 3 换成 `tcgen05` 跨过这条线。

`tcgen05.mma` 一条指令最大 128×256×16（单 CTA）；两个 CTA 合作（`cta_group::2`）时 M 可以到 256（[33 §4.4](../course/33_2cta_gemm/README.md)）。

## 5. Tensor Memory（TMEM）

TMEM 是每个 SM 上专供 `tcgen05` 使用的一块存储，用来放 MMA 的累加器。

```
          column 0                                  column 511
lane   0  ┌───────────────────────────────────────────────┐   ← warp 0（% 4）只能访问 lane 0–31
  ...     │      每个格子 32 bit                          │   ← warp 1：lane 32–63
lane 127  └───────────────────────────────────────────────┘   ← warp 2：64–95，warp 3：96–127
TMEM 地址 = (lane << 16) | column
```

| 规则 | 说明 | 哪一关讲 |
|---|---|---|
| 分配按列 | `tcgen05.alloc` 一次分配 2 的幂个列（32–512），总是包含全部 128 lane；用完必须 `dealloc` | [31 §4.1](../course/31_tcgen05_gemm/README.md) |
| 访问按 warp 分段 | warp w 只能访问 lane `32·(w%4)` 到 `32·(w%4)+31` | [31 §4.2](../course/31_tcgen05_gemm/README.md) |
| 读写是异步的 | `tcgen05.ld`/`st` 之后要 `tcgen05.wait::ld`/`wait::st` | [31 §4.6](../course/31_tcgen05_gemm/README.md)、[34 §4.5](../course/34_fa3/README.md) |
| 跨线程交接要 fence | `tcgen05.fence::before_thread_sync` → 同步 → `tcgen05.fence::after_thread_sync` | [31 §4.7](../course/31_tcgen05_gemm/README.md)、[34 §4.7](../course/34_fa3/README.md) |

512 列意味着一个 SM 上的 TMEM 只能放下两个 128×256 的 FP32 累加器。32 关用它做累加器双缓冲（[32 §4.4](../course/32_ws_gemm/README.md)），34 关在里面放 S 和 O（[34 §5.1](../course/34_fa3/README.md)）。

## 6. TMA 与 mbarrier

**TMA（Tensor Memory Accelerator）**是 SM 上专门搬运多维数据块的硬件。一个线程发出一条指令，硬件把整个 box 在 global 与 shared memory 之间搬完，其他线程不参与（[30 §4.1–4.2](../course/30_tma_mbarrier/README.md)）。

| 概念 | 说明 |
|---|---|
| tensor map | 128 字节的描述符，在 host 上用 `cuTensorMapEncodeTiled` 编码一次，描述张量的形状、步长、box 大小与 swizzle |
| box | 一次搬运的数据块，每维最多 256 个元素 |
| swizzle | 写入 shared memory 时按 XOR 打乱 16 字节块的位置，避免 bank conflict；`tcgen05` 的操作数也要求这种布局（[30 §4.3](../course/30_tma_mbarrier/README.md)） |
| multicast | 一次读取同时写进 cluster 中多个 CTA 的 shared memory（[33 §4.5](../course/33_2cta_gemm/README.md)） |

**mbarrier** 是 shared memory 中一个 8 字节的同步对象。它记录当前 phase、待到达次数、待完成的字节数（tx-count）。两者都归零时，phase 完成并翻转 parity；等待者用 parity 判断是否完成（[30 §4.4](../course/30_tma_mbarrier/README.md)）。

TMA 的 load、`tcgen05.commit` 都把完成信号发给 mbarrier。所以 mbarrier 是部分 3、4 中所有异步流水的“接力棒”。

**proxy**：普通 `ld`/`st` 属于 generic proxy；TMA 与 `tcgen05` 属于 async proxy。同一块 shared memory 先被普通指令写、再被 TMA 读时，每个写线程都要先执行 `fence.proxy.async.shared::cta`（[30 §4.5](../course/30_tma_mbarrier/README.md)）。这类错误测试和 racecheck 往往都发现不了（见 [工具指南 §3.1](tools.md#31-sanitizer-看不到什么)）。

## 7. cluster 与 CTA pair

**cluster** 是一组保证同时运行、放在同一个 GPC 上的 CTA（[33 §4.1](../course/33_2cta_gemm/README.md)）。

| 项目 | 数值 / 说明 | 来源 |
|---|---|---|
| cluster 大小 | 可移植上限 8 个 CTA | 规格 |
| DSMEM | cluster 内的 CTA 可以访问彼此的 shared memory、到达彼此的 mbarrier | 规格 |
| CTA pair | 2 个 CTA 组成一对，由 leader 的一个线程发出 `tcgen05.mma.cta_group::2`，合算一个 256×256 的 tile。A、B 各有一半放在对方的 shared memory 里，所以两个 SM 共用一份 B | [33 §4.4](../course/33_2cta_gemm/README.md) |
| 驻留数 | 每 SM 1 个 CTA（225 KB smem）时：cluster 2 → 74 个（148 SM 全用）；cluster 4 → 33 个（只用 132 SM） | 实测（`cudaOccupancyMaxActiveClusters`） |

cluster 4 用不满 148 个 SM，是因为每个 GPC 的可用 SM 数不一定是 4 的倍数。
